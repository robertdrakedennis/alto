# Alto working rules

## Search

- Use FFF first for all discovery.
- Use `find_files` for filenames/modules and `grep` or `multi_grep` for identifiers and content.
- Use `rg` only for raw text, regex, freshness checks, or when FFF is unavailable.

## No magic numbers

- Every number in code is one of three things:
  - a **symbol** from the content-symbol registry, for any obj, npc, loc, param, enum, struct, inv, varp, varbit, varc, seq, spot, dbtable, dbrow, interface, component or script id;
  - a value from a **generated revision table** (packet opcodes in `revisions/<rev>/protocol/`, CS2 opcodes in native910's book);
  - a **named constant** whose name states its meaning (a field width, a mask, ticks per second).
- Raw ids, coordinates and unnamed literals in engine, content, systems or tests are bugs. Coordinates and tables belong in data.
- Resolve ids against the content registry and the cache; never guess. Content-binding regeneration currently uses maintainer-local tooling. See `docs/symbols.md`.
- Places are named too: a tile content teleports to, spawns at or keys by is a `location` symbol in the content registry.
- Rust uses `rs910_symbols::{obj, varbit, component, ...}` (generated by `sym gen`, never edited).
- Gate ratchets count the remaining unnamed id literals in Rust (the `magic-ids` step). The count only goes down, and new files must be clean.

## Our own client

- The Rust client is our own engine, not a translation of anyone else's code. New and touched code uses real names, typed state and engine-shaped modules. No obfuscated-style identifiers (numbered `method`, `field`, `arg`, `var` names), no source-file cites into other projects, no transpiled or machine-generated ports, no copied shader text or game data.
- Behaviour stays exact where it is observable: packet bytes, the `ClientOptions` codec, per-tick game and variable state, CS2 semantics and hook order, pixels of the reference renderer, and the order of the logic phases. `tools/refactor/gate.sh` enforces this.
- Behaviour is the contract; structure is free. Once a subsystem is **sealed** (fully implemented and covered by replays, goldens or recorded fixtures) its function shapes, ownership, data layout, module and crate boundaries and names may be reshaped. Unsealed subsystems stay close to the behaviour they are still being written to match.
- `#[allow(clippy::too_many_arguments)]` is a temporary exception on sealed code: replace it with typed parameters or owned state when the subsystem is reshaped.
- Provenance for a fact belongs in the pull request, not in the code. `tools/refactor/provenance.py` ratchets traces of the original implementation down.
- Gate every change before merging: `CARGO_TARGET_DIR=<your dir> tools/refactor/gate.sh --base main` (it runs only what the diff needs and records a pass; `--full` runs every step and crate). The lead merges an already gated tree with `tools/refactor/gate.sh --verify-record --base main`, which passes in seconds when the tree and options match a recorded pass. One gate runs per machine at a time (others wait). Keep one target dir per lane and leave incremental compilation on (`tools/refactor/README.md`, "Gate"). Clippy is at zero and CI denies warnings. Rules and gates: `docs/engineering.md`, `tools/refactor/README.md`.
- Revision-specific facts (opcodes, packet layouts, config and CS2 opcodes, formats) live in the protocol, config and `native910` tables, never as literals in engine layers.
- `tools/Cargo.toml` is the Rust workspace (`native910`, `client910`, `tools/client910/crates/rs910-*`; one lockfile, target dir `tools/target`). New crates follow `tools/README.md`.
- The modern renderer (`rs910-render-modern`, `--renderer modern`, the default; `--renderer faithful-gpu` or `classic` is the reference renderer) is one renderer with quality settings (`ModernSettings`): no per-lane switches, and no revision or lane names in identifiers. Read `docs/renderer/modern-renderer.md` before changing it.

## Priorities

- The client comes first: packet dispatch, CS2 host, input, state, rendering, audio and the session lifecycle in the ordinary client runtime. It is at functional parity; client bugs still outrank content.
- A content slice is done when the real Rust client plays it: prove it with a session replay, not only server tests.
- A parser, packet builder, isolated test or server fixture is not a completed client feature. Connect the normal input and network path to its real consumer and verify the result.
- Missing client-owned audio, map, social, graphics and session services remain required client work. A `partial` settings control does not waive its missing client consumer.
- Current feature status: `docs/client-status.md`.
- Longer term: an open-source engine and studio (interface editor, map editor, CS2 IDE, "everything is a node"), see `docs/engine-and-studio.md`. Client completion stays first; build the studio seams inside the completion work (node and entity ids, component creator identity, per-group cache invalidation, a scripted-server `Io`, render-to-texture, generated protocol and CS2 tables, per-square scene build). Content pipeline (lossless repack, publish, hot reload) and reflection come before any editor.

## Testing

- Keep four thin checks: packet encode and decode byte equality, `ClientOptions` v38 codec and clamping, movement/varp/varc state per tick, CS2 stack/branch/var semantics.
- One harness: fast `cargo test` on demand. Thin checks nightly. Full pixel comparisons only before a release.
- Record observable behaviour once into a fixture beside the owning crate and compare against it. Do not add reference harnesses to the repo. Tests read committed recordings (`tools/client910/fixtures/recorded/`, the golden directories beside it, `tools/native910/tests/fixtures/`); the default suite and the gate need no other runtime and no original client. `tools/protocol-reference/` is not a recording: it is generated from `revisions/<rev>/protocol/*.tsv`, and the recording that anchors those tables is `tools/client910/fixtures/recorded/protocol-<rev>/`.
- Settings: one package for four-tab entry, navigation and persistence. A control without its backend (audio playback, particle or skybox, HD water) is `partial`, not failed. Do not block work on absent consumers.
- Doc diet: no new per-slice report, wave or verification files. Status lives in `docs/client-status.md`.

## Public repository scope

- This repository publishes the Rust client, native tools and recorded fixtures. The development server, `packages/`, `web/` and their npm manifests stay local and untracked. Never add them to public commits or history.

## Never commit

- The game cache (`server/data/cache/`, `server/data/pack/`), player data (`server/data/players/`), original client jars or source, decompiled code, shader text or any other game asset. These are supplied locally and stay gitignored.

## Maintainers only: local-only material (not in the public repository)

These live in the maintainer's checkout under gitignored paths and are never committed. Contributors do not need them.

- `ref/` holds local reference material, including `ref/archive-docs/` (the archived historical porting documents: phase logs, audits, research data, the earlier ledger with its source mappings, code-quality programme and renderer lane log) and `ref/independence/` (the independence audit and removed harnesses).
- `client/` (a local reference client with its build), `lib/` and `phase-g-inputs/` are gitignored. When implementing new behaviour, read the reference for exact behaviour, then write that behaviour in engine shape with our own names (no line-by-line translation) and verify with recordings and replays, not by structural resemblance. Do not make a default test read `client/` or run a JDK.
