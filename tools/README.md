# tools/: the Rust workspace

`tools/Cargo.toml` is one Cargo workspace: `native910`, the `client910` shell
and the `rs910-*` crates in `client910/crates/`. There is one lockfile
(`tools/Cargo.lock`) and one target directory (`tools/target`, release
binaries in `tools/target/release/`) unless `CARGO_TARGET_DIR` is set. The
toolchain is pinned in `rust-toolchain.toml`. Crate roles and the dependency
rules are in [`docs/architecture.md`](../docs/architecture.md).

| Member | What |
|---|---|
| `native910` | The cache codecs and the CS2 virtual machine. Edition 2024, its own strict lints; depends on no workspace crate. See `native910/README.md`. |
| `client910` | The shell: window, input, backend choice, the `client910` binary, plus the integration-level test suites. |
| `client910/crates/rs910-core` | std-only leaf utilities. |
| `client910/crates/rs910-jobs` | Safe scoped CPU work on bounded persistent Rayon workers, ordered results and inline mode. |
| `client910/crates/rs910-symbols` | The content-symbol registry's Rust bindings (id newtypes, named constants), generated by `sym gen` (`docs/symbols.md`). No dependencies. |
| `client910/crates/rs910-js5` | Cache, disk store, JS5 network client. |
| `client910/crates/rs910-protocol` | Wire protocol tables, framing, message parsers and builders. |
| `client910/crates/rs910-config` | Config decoders and stores, the client options codec. |
| `client910/crates/rs910-game` | Entity and game state, packet appliers, variable domains, session state machine. |
| `client910/crates/rs910-model` | CPU model layer: models, animation, particles, floors. |
| `client910/crates/rs910-scene` | CPU scene layer: map loading, scene graph, occlusion, camera, minimap, `SceneSnapshot`. |
| `client910/crates/rs910-audio` | Audio stack. |
| `client910/crates/rs910-toolkit` | The 2D toolkit boundary: display lists, batches, the `Toolkit` trait, `FramePlan`. |
| `client910/crates/rs910-ui` | The retained UI: components, CS2 host, menus, console, world map, social. |
| `client910/crates/rs910-gpu-device` | The wgpu device layer. |
| `client910/crates/rs910-render-gpu` | The 2D/UI toolkit: UI, text, interface models, minimap base, composition around the scene, screenshots. |
| `client910/crates/rs910-far-scene` | Render-only far scene, CPU half. |
| `client910/crates/rs910-render-modern` | The scene renderer (`docs/renderer/modern-renderer.md`). |
| `client910/crates/rs910-client` | Client core, session and login I/O, record and replay. |

```sh
cargo run --release --manifest-path tools/client910/Cargo.toml -- --pack-root /path/to/pack
cargo test --manifest-path tools/client910/Cargo.toml --lib          # client910 fast suite
cargo test --manifest-path tools/client910/crates/rs910-core/Cargo.toml   # one crate
cargo test --manifest-path tools/Cargo.toml --workspace --lib       # every crate
cargo test --release --manifest-path tools/native910/Cargo.toml      # native910
tools/check.sh                                                       # generated tables, fmt, clippy, provenance
```

Add `--features no-pack` to any of these on a machine without
`server/data/pack`.

Other directories: `perf/` (renderer and client benchmarks, see its README),
`provenance/` (the provenance count, see `provenance.py`), `oracle/` (GPU pixel
comparison helpers), `revision/` (generators for the per-revision registries
under `revisions/`: `gen_protocol.py` writes the client and test packet
tables from `revisions/<rev>/protocol/*.tsv`; `tools/check.sh` checks
them) and `protocol-reference/` (the generated packet table the tests read).
`licenses.py` regenerates `THIRD_PARTY_LICENSES.md` from
the Rust lockfiles (run it after changing a lockfile; `--check` reports
a stale file).

## Crate conventions

- **Name and place.** `rs910-<layer>` under `tools/client910/crates/`, a
  workspace member in `tools/Cargo.toml`, edition 2021, `publish = false`,
  `[lints] workspace = true`, `[lib] doctest = false`. Its allowed workspace
  dependencies follow the layering in `docs/architecture.md` (`rs910-core`
  is std only).
- **Splitting across a fence.** When a module holds wgpu or winit items, the
  fenced items live in a `<module>_gpu` or `<module>_winit` module in the crate
  that may use the external crate. Shared data goes below both. Where the UI
  needs something native, the seam is plain data the native side fills or a trait
  it implements.
- **`pub` surface.** Items other crates reach are `pub`; nothing else changes
  visibility. Crate roots declare `pub mod` per module plus crate-wide types.
- **Errors.** A crate without `anyhow` returns its own error type
  (`rs910_core::Error`, built with `rs910_core::err!` and `ensure!`).
  Decoders that keep their own error types wrap the shared reads in
  `rs910_core::reader`.
- **Test-only code.** Code that runs only under `cfg(test)` does not run in a
  dependent crate's tests. Make it `cfg(any(test, feature = "test-hooks"))`; the
  shell enables `test-hooks` through `[dev-dependencies]` only. Production never
  enables it.
- **Tests.** Unit tests live with their module. Tests that need shell fixtures,
  `test_support` or the pack live in `client910` (golden and replay suites).
  Shared helpers sit below the crates that use them, behind `test-hooks`
  (`rs910_core::test_support`, `rs910_js5::test_support`).
- **Features.** Every workspace crate has a `no-pack` feature (tests that read
  `server/data/pack` are `#[cfg_attr(feature = "no-pack", ignore)]`), and the
  shell's `no-pack` forwards to its dependencies.
- **Diagnostics.** A crate that reads `CLIENT910_*` variables owns them in its
  own parse-once module named for its layer (`ui_debug_flags`,
  `render_debug_flags`, ...). The shell's `debug_flags` keeps the rest and `main`
  forces every set at start-up.
- **Logging.** A `log` record's target is its module path, so a crate logs as
  `rs910_<layer>::module`. The shell's stderr logger prints `client910*` and
  `rs910_*` targets.
- **Lints.** A `pub` item of a `pub mod` is never dead code; use
  `#[allow(dead_code, reason = ...)]` rather than `#[expect]` on it.
- **Merging duplicates.** Before one copy replaces another, prove them equal in
  the merging change (exhaustively for small domains, over dense grids, edge
  values and random corpora otherwise) and put the evidence in the pull request.
  Do not keep a frozen copy of the old code as a permanent test. Copies that
  differ are behaviour findings: keep the correct one and document the
  difference with a test.
- **Assets.** Data a module `include_bytes!`s moves with it. Data the client can
  compute is generated at run time and pinned by a digest test, not shipped.
- **Fences.** wgpu: `rs910-gpu-device`, `rs910-render-gpu`, `rs910-render-modern`
  (the shell keeps it as a dev-dependency for GPU tests). winit: the shell. tokio:
  `rs910-js5` and `rs910-client`. cpal: `rs910-audio`.
