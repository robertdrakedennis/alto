# tools/: the Rust workspace

`tools/Cargo.toml` is one Cargo workspace: `native910`, the `cs2` donor toolkit, the `client910` shell
and the `rs910-*` crates in `client910/crates/`. There is one lockfile
(`tools/Cargo.lock`) and one target directory (`tools/target`, release
binaries in `tools/target/release/`) unless `CARGO_TARGET_DIR` is set. The
toolchain is pinned in `rust-toolchain.toml`. Crate roles and the dependency
rules are in [`docs/architecture.md`](../docs/architecture.md).

| Member | What |
|---|---|
| `native910` | Standalone CS2 and cache library and CLI. Edition 2024, its own strict lints; depends on no workspace crate. See `native910/README.md`. |
| `cs2` | Revision-bound donor decoder, semantic importer and evidence CLI. Consumes native cache primitives and the client config schema layer; production client and native910 code do not depend on donor tooling. The client replay uses it through a dev-dependency. |
| `client910` | The shell: window, input, backend choice, the `client910` binary and the `drawdiff`, `floordiff` and `scenediff` comparison tools, plus the integration-level test suites. |
| `client910/crates/rs910-core` | std-only leaf utilities. |
| `client910/crates/rs910-symbols` | The content-symbol registry's Rust bindings (id newtypes, named constants), generated by `sym gen` (`docs/symbols.md`). No dependencies. |
| `client910/crates/rs910-js5` | Cache, disk store, JS5 network client. |
| `client910/crates/rs910-protocol` | Wire protocol tables, framing, message parsers and builders. |
| `client910/crates/rs910-config` | Config decoders and stores, the client options codec. |
| `client910/crates/rs910-game` | Entity and game state, packet appliers, variable domains, session state machine. |
| `client910/crates/rs910-model` | CPU model layer: models, animation, particles, floors. |
| `client910/crates/rs910-scene` | CPU scene layer: map loading, scene graph, occlusion, camera, minimap, `SceneSnapshot`. |
| `client910/crates/rs910-audio` | Audio stack. |

| `client910/crates/rs910-gpu-device` | The wgpu device layer. |
| `client910/crates/rs910-render-gpu` | The reference GPU toolkit. |

`refactor/rsscan` (the gates' syn-based scanner) is its own workspace and is
excluded from this one.

```sh
cargo run --release --manifest-path tools/client910/Cargo.toml -- --pack-root /path/to/pack
cargo test --manifest-path tools/client910/Cargo.toml --lib          # client910 fast suite
cargo test --manifest-path tools/client910/crates/rs910-core/Cargo.toml   # one crate
cargo test --manifest-path tools/Cargo.toml $(python3 tools/refactor/workspace.py --pkg-args) --lib
                                                                     # client910 + every rs910-* crate
cargo test --release --manifest-path tools/native910/Cargo.toml      # native910
tools/refactor/gate.sh --base main                                   # every quality gate (--full: every crate)
```

Add `--features no-pack` to any of these on a machine without
`server/data/pack`.

Other directories: `perf/` (renderer and client benchmarks, see its README),
`refactor/` (the quality gates, see its README), `oracle/` (GPU pixel
comparison helpers), `revision/` (generators for the per-revision registries
under `revisions/`: `gen_protocol.py` writes the client and test packet
tables from `revisions/<rev>/protocol/*.tsv`; the gate's `generated` step checks
them) and `protocol-reference/` (the generated packet table the tests read).
`licenses.py` regenerates `THIRD_PARTY_LICENSES.md` from
the Rust lockfiles (run it after changing a lockfile; `--check` reports
a stale file).

## Crate conventions

- **Name and place.** `rs910-<layer>` under `tools/client910/crates/`, a
  workspace member in `tools/Cargo.toml`, edition 2021, `publish = false`,
  `[lints] workspace = true`, `[lib] doctest = false`. Its allowed workspace
  dependencies are its row in `tools/refactor/layers.txt` (`[crates]`); a crate
  whose external dependencies are restricted has an `[externals]` row
  (`rs910-core` is std only). `dag-check.py` checks both against
  `cargo metadata`.
- **Modules.** Every production module is listed in `layers.txt` under the crate
  it lives in; the check fails on an unmapped module. Module names are global in
  the DAG scan, so a module gets a distinct name.
- **Splitting across a fence.** When a module holds wgpu or winit items, the
  fenced items live in a `<module>_gpu` or `<module>_winit` module in the crate
  that may use the external crate. Shared data goes below both. Where the UI
  needs something native, the seam is plain data the native side fills or a trait
  it implements.
- **`pub` surface.** Items other crates reach are `pub`; nothing else changes
  visibility. Crate roots declare `pub mod` per module plus crate-wide types.
- **Errors.** A crate without `anyhow` returns its own error type
  (`rs910_core::Error`, built with `rs910_core::err!` and `ensure!`).
  Decoders that keep their own error types wrap the shared reads in
  `rs910_core::reader`.
- **Test-only code.** Code that runs only under `cfg(test)` does not run in a
  dependent crate's tests. Make it `cfg(any(test, feature = "test-hooks"))`; the
  shell enables `test-hooks` through `[dev-dependencies]` only. Production never
  enables it.
- **Tests.** Unit tests live with their module. Tests that need shell fixtures,
  `test_support` or the pack live in `client910` (golden and replay suites).
  Shared helpers sit below the crates that use them, behind `test-hooks`
  (`rs910_core::test_support`, `rs910_js5::test_support`).
- **Features.** Every workspace crate has a `no-pack` feature (tests that read
  `server/data/pack` are `#[cfg_attr(feature = "no-pack", ignore)]`), and the
  shell's `no-pack` forwards to its dependencies.
- **Diagnostics.** A crate that reads `CLIENT910_*` variables owns them in its
  own parse-once module named for its layer (`ui_debug_flags`,
  `render_debug_flags`, ...). The shell's `debug_flags` keeps the rest and `main`
  forces every set at start-up.
- **Logging.** A `log` record's target is its module path, so a crate logs as
  `rs910_<layer>::module`. The shell's stderr logger prints `client910*` and
  `rs910_*` targets.
- **Lints.** A `pub` item of a `pub mod` is never dead code; use
  `#[allow(dead_code, reason = ...)]` rather than `#[expect]` on it.
- **Merging duplicates.** Before one copy replaces another, prove them equal in
  the merging change (exhaustively for small domains, over dense grids, edge
  values and random corpora otherwise) and put the evidence in the pull request.
  Do not keep a frozen copy of the old code as a permanent test. Copies that
  differ are behaviour findings: keep the correct one and document the
  difference with a test.
- **Assets.** Data a module `include_bytes!`s moves with it. Data the client can
  compute is generated at run time and pinned by a digest test, not shipped.
- **Fences.** wgpu: `rs910-gpu-device`, `rs910-render-gpu`, `rs910-render-modern`
  (the shell keeps it as a dev-dependency for GPU tests). winit: the shell. tokio:
  `rs910-js5` and `rs910-client`. cpal: `rs910-audio`.

## Modern CS2 donors

The `cs2` CLI consumes an explicit profile from `revisions/<build>/cs2/`.
Profiles bind the client MD5, script index SHA-256, every registered operand
layout, recovered command names and unverified symbol hints. Byte decoding is
independent of semantic coverage. A name in `symbol_hint` is never used as a
command mapping. New revisions require new profiles; none fall back to another
revision or an unscrambled book.

```sh
cargo run --manifest-path tools/cs2/Cargo.toml -- \
  --profile revisions/950/cs2/950-1.json scan \
  --cache-root ref/donors/950-1/openrs2-2721 \
  --build 950.1 --client-md5 290cb3489d088d145741f1734f53b0fc \
  --output /tmp/cs2-950.json
```

The cache root holds OpenRS2 raw containers (`255/<archive>.dat` for indices,
`<archive>/<group>.dat` for groups). Every indexed script must be present and
pass its checksum, bounded decode and byte round trip. The report pins its
profile and corpus, gives opcode occurrence counts and operand samples, and
retains unresolved semantics. The MD5 argument asserts which Ghidra program
supplied the profile; it does not hash a locally opened client binary. Outputs
are new immutable files. `dump --input <uncompressed-script>` writes lossless
JSON, including raw string bytes and switch offsets.

`uses --cache-root <export> --command cc_create --output <new-report.json>`
returns every matching call site, with original instruction PCs, merged context,
script hashes, argument/local counts and handler registration facts. Repeat
`--command` or `--opcode` to select a union; numeric selection also accepts
unresolved registered rows. Command names select profile registration rows,
while operand-specific normalized operations appear in the context. `--before`
and `--after` set context widths (defaults four and three); zero emits only the
matching instructions. Every indexed script is checksum-verified and byte-round-tripped,
including scripts with no match. The report pins the profile, client, script index
and full corpus, and preserves raw context if normalization fails.

`normalize` accepts the same `--input` or `--script`/`--cache-root` inputs as
`dump`. It emits named operations, typed literals, local lanes, absolute branch
and switch targets, and exact source operands. The 950.1 string policy drops the
five unassigned Windows-1252 bytes, unlike 910's `?` policy. Unknown identities
and unknown string/switch policies remain explicit; internal constant-pool indices are
never mistaken for long literals. Reconstructing the wire representation retains
unused switch tables, duplicate keys, opaque instructions and raw string bytes.
This representation describes the donor. Target behavior, host suspension,
component capabilities and content references still require importer proofs.

`closure` follows reviewed active-component and explicit-component callbacks,
using source addressing and descriptor contracts independently of target opcode
names. The recorded modern transmit installer retains its trigger list when a
replacement has no positive `Y` count; a nonempty retained list removes the
descriptor's final UTF-8 byte even without `Y`. Positive counts give fixed traffic;
otherwise unknown retained state stays unresolved. Descriptor recordings extend
the existing thin CS2 check. The actual colour-helper closure now exposes its
five-integer theme callback and the callback's child-selection use; the transmit
event's player-variable source ring is identified. The portable retained-player
consumer keeps trigger vectors across replacement and clear, preprocesses UTF-8
bytes before building typed arguments, and uses unsigned cursor ordering and
empty-list filtering on the ordinary player ring. Eleven original descriptor
cases and fourteen event-walk cases extend the existing thin component check.
An independently authored installer is built with pinned execution metadata and
reaches a runtime child through a framed script packet; a live server variable
change queues its callback, substitutes the child identity, and paints the
result. The donor's installer bridge, named trigger translation and complete
colour-helper callback import remain unsealed.

`database --cache-root <export> --schema revisions/950/cs2/database.json
--output <local.json>` decodes every DB table and row after checking both the
script and config archive index identities and each definition group's CRC.
Add `--row <id> --field <packed-field> --index <tuple-row>` to inspect a field's
selected types, effective values and complete-column row count. The report
retains definition IDs, file hashes, names, reserved headers and typed values;
coordinate components use exact float bits. Keep generated donor reports local.
The shared client config layer owns the codec, typed tuple projection and an
engine resource image. Pass `--database-schema revisions/950/cs2/database.json`
to `closure`, `prepare` and `import` for database-backed scripts. Closure output
shows the reaching packed field, selected type IDs and stack output counts.
Preparation pins the schema, source profile, config index and resource image;
importing requires the same verified definitions. Generated field/count bridges
carry the resource with their script-group execution metadata, preserve original
arguments and field identities, and cache decoded data by its immutable digest.
Resource bytes survive repacking and source dump/rebuild; removing or changing
them invalidates the imported bytecode. No target config archive is overwritten.

Field imports currently require a constant packed field at each use. They support
integer, text and long tuple outputs, table fallback, typed defaults and retained
prefix pushes on failure. The existing client replay checks the recorded scalar
observations through the VM and displays database-backed authored text through
ordinary packet hooks, pointer input and painting. Coordinate values remain
losslessly inspectable but require tagged VM objects before import. Dynamic field
contracts, donor session-service-mode binding and base-tag mismatch failure
classes remain unsealed. The selected complete color-helper closure uses the
normal client route described below.

`enums --cache-root <export> --schema revisions/950/cs2/enums.json
--output <local.json>` checks the exact script and enum indices and every enum
container CRC before decoding all definitions. Add `--enum-id <id>` to inspect
one definition, and `--input-type <serial> --output-type <serial> --key <key>` to
query it. Reports retain both sparse and dense values, declared nullable types,
defaults, the last block's wire count, ignored tags, consumed length, trailing
byte count and each file hash. Generated reports and resource images stay local.
The matching 950.1 export contains 16,742 enums, with no ignored tags or tails.

The shared config layer owns modern enum decoding, effective lookup and a
canonical resource image. The recorded defaults are integer zero and empty text;
repeated sparse blocks merge and overwrite keys. Equal dense capacity resets its
entries; a different positive capacity retains an existing allocation, and zero
capacity reveals the sparse map again. Unsupported out-of-allocation writes are
rejected by the bounded reader. Source `enum` analysis uses the reviewed string
serial: only that serial returns an object, while other declared output types
return an integer. Dynamic enum IDs retain known traffic, and an unknown reaching output
type remains unresolved. Closure reports expose the reaching enum, key and type
arguments. Numerical decoder and query observations extend the existing thin
check, with no additional test entries.

Pass `--enum-schema revisions/950/cs2/enums.json` to `prepare` and `import` for
enum-backed scripts. The plan pins the source profile, enum schema, enum index
and canonical resource hash. Each query gets a generated consumer with the
reviewed output serial and string serial; dynamic enum IDs and keys retain their
ordinary values. The VM reads the bound resource through the normal client host,
checks declared types, preserves integer bits and string results, and caches the
decoded library by its immutable digest. Removing the resource or changing its
binding invalidates the imported bytecode. The existing UI replay runs the
recorded queries through the VM, preserves failure prefixes, rebuilds a dumped
enum adapter, and applies authored enum text and a dynamic palette through
ordinary packet hooks, pointer input and painting. Donor session-service-mode binding and the
original tag-mismatch abort class remain unsealed. The selected modern theme
callback uses the normal client route described below.

`variables --cache-root <export> --schema revisions/950/cs2/variables.json
--output <local.json>` verifies the exact script/config indices and the group
CRCs, then decodes all source base variables and varbits. Add `--script <id>` to
inspect the proven script closure's variable uses, or `--varbit-id <id>
--base-value <integer>` to apply a recorded getter to a supplied value. Reports
retain full source IDs, primary/secondary registry selection, base definitions,
declared types, lifetime/transmit fields, legacy defaults, inclusive ranges,
flags, ignored tags, file hashes, consumed lengths and tails. Missing source
definitions, unbound bits and unreviewed domain getters stay explicit gaps.
Direct variable uses include their full base-definition contract too. These
source identities are not bindings to the target client.

The matching export contains 62,146 varbits and 26,708 variables in seven
registered domains, with no decode failures or ignored tags; 2,882 bits remain
unbound. The modern variable decoder accepts tags that the 910 decoder rejects,
and the recorded player/client range arithmetic wraps both shifts: a full
32-bit range returns zero. Defaults depend on the declared type and domain's
legacy policy. The original decoder loops, player/client bit getters and default
selectors are recorded with synthetic inputs beside the existing CS2 check;
there are no new test entries. Full constructor/lifetime behavior, sparse and
persistent service modes, other domain bit getters, writes and abort classes
remain unsealed. The palette closure now exposes its three bit reads over two
integer bases, both defaulting to zero. `prepare` and `import` accept
`--variable-schema revisions/950/cs2/variables.json --variable-symbols
revisions/910/symbols`. Preparation lists every required source base with an
unbound `target`; supply a qualified symbol such as `varp.interface_layout` or
`varc.interface_theme_preview`. Import pins the source definitions, target config
and symbol registry, requires the same state owner and integer default, and
records the resolved symbol, target ID and definition hash. Source IDs are never
used as target fallbacks. Each source bit gets a use-specific adapter containing
its reviewed shift and mask; the ordinary host reads the live base variable and
checks the bound integer default before applying those source semantics. This
also preserves nonzero secondary registry selection and wide source IDs.

Modern flat-child selection has a separate source contract from category
selection. Its source selector chooses the secondary target for any nonzero
byte. The source range check happens before parent loading: invalid child
identities preserve both active references; valid misses clear both. Direct
children precede the retained owner index, and the accepted flat range is wider
than the category opcode's bank range. A generated use keeps the original
parent and encoded child arguments and carries the revision's limit in its
portable consumer. The existing thin check compares twelve original handler,
lookup and selection recordings. The ordinary UI replay imports an authored
modern selector, delivers it through framed script packets, paints a selected
runtime child and preserves its colour on a missed selection. Original child
creator defaults remain unfinished.

The existing thin check executes recorded modern getters through those VM
adapters, including full-width/reversed ranges and retained failure prefixes.
The ordinary authored UI replay imports independently authored palettes with
source bit IDs above the target codec's width, changes both real variable owners,
and runs the palette through framed `RUNCLIENTSCRIPT` packets into an existing
label. `ALTO_MODERN_PALETTE_CASE=<local.json>` selects a real archived closure;
its case pins `cache_root`, `procedure`, `source_sha256`, named `bindings`, and
numerical `observations` (`player`, `client`, `key`, `colour`). Actual 950 palette
10495 and selector 15721 execute through this path with theme changes, preview
overrides and fallback keys. Donor resources and the local case stay uncommitted.
The selected full color helper and its callback also run on a modern-created
text child as described below. Modern geometry and other constructor/variable
consumers remain required.

`revision/extract_cs2_registry.py` is an optional Capstone-based extractor for
constant x86-64 initializer registrations. Supply a local hex export and the
observed code/table bounds, stride and field offsets. It tracks constants only
inside basic blocks and rejects incomplete, repeated or unknown registration
values. It does not infer command meanings, execute control flow or analyze
indirect stores. Keep original exports, caches and detailed evidence in `ref/`.
`revision/gen_cs2_profile.py` combines those local registrations, reviewed
decoder facts and a Ghidra function export. The export supplies hints only.
`--check` compares the generated profile without writing.

The generated profile is a revision table; a successful corpus scan is byte
format evidence, and an imported feature still needs resource mapping and a
normal client replay.


## Modern CS2 imports

`cs2` separates the donor wire profile from the reviewed target adapter. The
950.1 profile is pinned to its client MD5 and script archive index; the adapter
checks every selected registration's handler, encoding and identity against
that profile and every target opcode against the embedded 910 book. Recovering
an unrelated handler does not invalidate the reviewed mappings. There is no
nearest-revision fallback or script-ID reuse.

The workflow is `fetch`, `scan`, `normalize` or `closure`, `prepare`, then `import`.
`fetch --output <ignored-cache-directory>` selects the newest complete English
live cache for the exact profile build, then checks its script-index hash before
writing cache bytes. `--cache-id <id>` pins a particular archive snapshot. The
profile script archive is always fetched; repeat `--archive <id>` to include
additional data archives. The command records the highest archived build as
well as the selected build, so a newer unsupported revision stays visible.
Bounded HTTPS workers reuse connections, verify each raw group against its
index CRC, replace corrupt groups atomically and reuse valid groups on rerun.
`cs2-cache.json` pins the cache, profile and archive index hashes and records
which archives completed. An interrupted run retains verified groups; an OS
file lock prevents simultaneous fetches into one output. Direct API containers
have no two-byte version trailer. Cache data remains local and gitignored.

`closure` follows named calls and callback heads proven by complete typed
source flow. It reports each setter's descriptor, typed arguments, component
argument, value origins and installed, cleared, dormant, trapped or unreachable
status. Unknown heads, missing named or callback callees and unrecovered handlers
keep `dependency_complete` false; source-flow diagnostics identify the blocking
instruction. Reviewed analysis facts live in the wire profile separately from
target lowering rules. In the modern profile, reused locals begin unknown,
descriptors consume UTF-8 bytes, and positive trigger counts on the plain
operation hook trap. The ordinary 910 analyzer retains its existing defaults.
The importer can install or clear a proven operation callback when every body
has reviewed lowering. A generated procedure replaces each setter use while
keeping donor instruction indices and ordinary producer values unchanged. It
remaps the callback head, reconstructs the typed descriptor from source units,
and consumes the original descriptor and any nonpositive trailing-Y count.
Target call-context analysis follows the installed callback, verifies its exact
integer/string/long argument counts and carries component roles into its body.
Operation-callback integer and string values must be proven constants without
event substitutions; tagged objects outside the string lane, dormant heads, positive
plain-hook trigger counts and unresolved heads remain unsupported. The larger
“View” closure is inspectable; its remaining host handlers still prevent a port.
`prepare --cache-root <export> --script <donor-id> --name <export-name>
--base-pack <910-pack> --output <plan.json>` writes the donor closure hashes,
both target archive hashes, procedure names and typed scalar inputs. Edit a
component argument to `{"kind":"component","value":"interface/child"}` using
a curated target name. Keep scalar inputs as `{"kind":"input"}` or bind them
with `{"kind":"value","value":<integer>}`. Long inputs are `null`; fixed long
arguments are integers. `string_arguments` contains fixed string values; `null`
remains unbound and cannot be published. The plan can contain multiple named exports of one
procedure with different bindings.

For a helper that operates on an already selected frame, bind the export's
`active_component` to a curated `interface/child` spelling. Its bounded entry
setup selects that static frame in the primary bank before binding arguments
and calling the donor body. Setup preserves export argument initialization,
retained long stacks and source instruction/call accounting. The same reaching
edges used by VM analysis carry named frame ownership into host adapters and
normal calls. An active host use needs a named owner on every reaching path;
changing an inherited owner through a call remains unmodeled and is rejected.

A modern player-variable hook with a proven positive trailing-Y count gets a
use-specific retained installer. Its trigger-only variables also appear in the
plan's required bindings; each trigger is translated through a named live player
binding. The original producers and donor instruction indices remain unchanged.
The installer relinks the callback head and keeps dynamic captured integers.
Its metadata pins the source event token layout. Variable delivery projects
parent and child identities from 16-bit component words, supplies the recorded
zero/absent event fields and applies substitutions in sequence, including values
that become later tokens. Callback analysis gives the projected parent a named
component role and follows static and runtime-child reselection in the linked
body. Seven numerical recordings cover the original variable-request constructor
and integer argument loader in the existing thin check. String event tokens and
non-string tagged objects remain unsupported by this import path; a nonpositive
or absent Y needs a proven prior retained vector and is not guessed empty.


For a hardcoded donor component, add a `component_uses` entry with `procedure`,
`instruction` (the source instruction index) and `component` (a curated target
name). This changes the address consumed by that host use. Other copies of the
same integer keep their value. Each use appears in `import.json` with its
source instruction, generated procedure and linked callback IDs.

`import --cache-root <export> --adapter revisions/950/cs2/950-1-to-910.json
--plan <plan.json> --base-pack <910-pack> --inames <inames.txt>
--output <new-directory>` allocates fresh IDs for the whole call closure and
its bound export and host-use wrappers. It checks component kinds and every reachable text
consumer in its call context. A named component role follows copied values
through arguments and locals; equal numeric literals never acquire that role. The existing project builder publishes the
compiled archive, editable source, source maps, symbols, pinned build facts,
`import-plan.json` and `import.json`. Unedited group containers stay identical.
The result supplies script/interface packs; unchanged rendering/configuration
resources come from the pinned base installation.

Pass `--profile revisions/950/cs2/950-1.json` before each subcommand. The initial
adapter covers constants, integer/long local traffic, recovered branches,
return/calls, switches, wrapping add/subtract/multiply, operand-counted string
joins, explicitly bound plain-text writes, operation labels and visibility,
recursive runtime-child removal, schema-bound database field/count queries,
active and explicitly bound color/fill/transparency writes, and use-specific
operation callbacks. Component
bindings resolve any existing widget; each use then proves the needed capability
(text writes require a text widget, operation labels can also target a layer). Duplicate switch keys are resolved under the pinned donor
policy before target encoding (950 keeps the last entry; 910 selects the first).
Every emitted procedure, including export and host-use wrappers, must round-trip
through the target script codec before publication. Fixed values outside that
codec fail with the generated procedure identified.
String local copies and fixed string arguments are supported when typed
dataflow proves a non-null string on every reaching path, including joins and
calls. Other tagged object representations, direct variable reads/writes and other config IDs, richer widgets,
resumable operations and unrecovered handlers require further adapters.
Modern child removal uses a generated bridge with an explicit
`clear-runtime-children` host operation. It recursively empties retained runtime
child and drawing arrays, leaves cache-defined children intact, and succeeds
without changes for missing or non-container targets. Ordinary target scripts
retain their existing flat removal behavior. An unsupported host fails explicitly.
Runtime attachment keeps children ordered by identity. Separate drawing storage
is populated only by explicit reordering; an empty retained drawing list falls
back to the ordered children. Once populated, insertions append to drawing order
and replacements update the same identity in place. Four original-code numerical
recordings exercise these cases in the existing thin component check. Input,
layout, immediate hooks, animation and painting share the effective child order.
This seals the recorded attachment/order cases. The reviewed flat text creator
also binds a small immutable constructor resource to each generated use. It
consumes the original parent, kind and encoded child identity without changing
producer instructions, checks the child range before interface loading, traps
for a missing group, and preserves both selections for a missing or non-container
static parent. Factory kinds truncate to a byte. Import call-context analysis
requires a proven recorded text kind on every reaching path and a named container;
other and unresolved kinds remain unsupported. Nine numerical original-engine
cases cover creation traffic, attachment, both selector banks, boundary and no-op
paths, and the projected paint/aspect/text defaults in the existing thin check.
The creator records the linked source procedure and original instruction index,
rather than its bookkeeping adapter identity. A creation no-op may preserve its
old active reference, so ownership after creation survives only when both paths
agree on the same named frame. Other constructors, unprojected shared defaults,
nested creation and revision-specific admission remain unsealed.
A non-argument local must be written on every predecessor before it is read;
the importer never substitutes 910's fresh defaults for modern reused storage
or interprets an unclassified default object tag as a string.
Paint uses carry explicit host metadata with the reviewed change kind and
rectangle class mapping. Color stores all integer bits and schedules a client
change for static components in non-transient interfaces, including equal writes.
Fill changes rectangles only, comparing its integer input to one. Transparency
wraps to a byte. These consumers preserve component selection and avoid dirty
marks; ordinary target scripts keep their existing property consumers. Recorded
scalar cases cover these writes through the VM and retained property owner;
the authored packet/input/paint replay imports all six setter forms. The same
replay imports an independently authored colour helper and its retained callback.
A maintainer's `ALTO_MODERN_PALETTE_CASE` can add `colour_helper` with a pinned
`procedure`, `source_sha256` and numerical `observations` sharing one key/client
setting. The actual 950.1 four-procedure colour helper has passed this route:
framed `RUNCLIENTSCRIPT` executes an independently authored modern creator in an
existing named frame, then the archived helper sets the new text child's theme.
The constructor's zero bounds and absent font are observed before framed
